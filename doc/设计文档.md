Agentic 音频切分、合并、打标、评测平台 UI 与架构设计文档

1. 文档目标

本文档用于设计一个完整的 Agentic 音频切分、合并、打标、调听、标注、评测与数据资产平台。

平台核心面向以下场景：

* 门店接待录音分析；
* 销售/客服质检；
* 母婴、珠宝、保险、汽车试驾等线下服务场景；
* 长音频切分与客户组识别；
* ASR、VAD、Diarization、声纹、事件标签、质检标签、多模型评测；
* 汽车试驾、销售、交付、售后等场景中的业务单据与音频事件关联；
* 自动化评测与人工评测结合；
* 模型效果回流与 badcase 沉淀；
* 数据资产化、洞察分析与运营看板。

设计原则：

1. 对业务用户不暴露 Dagster、Asset、Materialization、Partition 等底层概念；
2. 对项目管理员、平台运营、模型团队和工程团队，在任务配置、模型配置、运行诊断和资产回填中渐进披露 Dagster Job / Op / Asset Key / IO Manager / Deps 等映射；
3. 对业务用户统一呈现为“数据资产”“数据回填”“资产血缘”“资产任务”“质量报告”；
4. 系统按“租户 → 项目 → 数据域 → 数据资产 → 任务/评测/洞察”分层；
5. 任务配置是任务类型、画布版本、任务版本、调度、A/B 实验、模型服务绑定、输出资产和外部回写的配置中心，不是独立的数据管理页面；
6. 调听、标注、评测、洞察必须保持时间、地点、人物、音频、事件、标签、业务单据的连续性；
7. UI 体验必须支持多皮肤、多语言、可解释动效和智能化交互；
8. 粒子风等高级视觉效果必须服务于音频、事件、Agent Trace、资产血缘等数据语义，不能只是装饰；
9. 平台不是单纯标注工具，而是音频数据资产与模型效果闭环平台。

1. 产品定位

1.1 平台定义

本平台是一个面向企业客户的 多租户音频数据资产与 Agentic 处理平台。

一句话定义：

围绕“时间、地点、人物、音频、事件、标签”构建连续数据上下文，
通过 Agentic 音频处理链路完成切分、合并、打标、评测和洞察，
最终形成可追踪、可复盘、可回流的数据资产平台。

在汽车等强业务流程场景中，平台还必须支持业务单据关联。

例如：

* 试驾预约单
* 试驾确认单
* 报价单
* 订单 / 合同
* 金融分期单
* 保险单
* 交付单
* 售后维修单
* 保养工单

这些单据不只是附件，而是事件关联对象。它们需要和音频片段、客户、销售、门店、车辆、时间、业务事件、标签结果建立可交互的证据链。

平台不是：

普通音频播放器
普通标注工具
普通 ASR 后处理系统
普通 BI 看板
普通工作流系统

平台是：

音频数据资产平台

* Agentic 音频任务运行平台
* 调听标注工作台
* 标签体系管理平台
* 自动/人工评测平台
* 模型效果回流平台
* 业务洞察平台

1. 底层架构与产品表达

3.1 底层架构

底层可以使用：

Temporal / Celery：
负责单条音频任务的长任务执行、重试、暂停、恢复、人工等待。
Dagster：
负责批量数据资产编排、数据回填、离线复算、评测结果生成、模型对比报告。
dbt：
负责 SQL 数据建模，把 raw 数据加工成标准事实表、指标表、看板表。
Agentic Runtime：
负责局部智能决策，例如边界冲突仲裁、低置信重跑、标签冲突解释、badcase 归因。
MySQL：
负责业务元数据、项目配置、标注数据、任务状态、权限。
MinIO / OBS / S3：
负责音频、ASR JSON、Diar JSON、模型输出、报告等文件资产。
Qdrant：
负责知识库、标签样本、证据片段、声纹 embedding 和 badcase 的向量检索。

⸻

3.2 产品表达和底层映射

任务配置是平台最重要的配置入口之一。它管理的不是一个孤立画布，而是：

任务类型
画布版本
任务版本
输入引用
处理节点
模型服务绑定
输出资产
外部回写
调度策略
A/B 实验
运行记录
发布和回滚

一个数据源或数据资产可以被多个任务类型画布引用；一个任务类型也可以拥有多个画布版本。生产主线、灰度候选、影子评测和热修复画布应在同一任务类型下统一管理。

11.3 全天时空音频 Minimap

全天时空音频 Minimap 是调听页的全局导航层，展示当前项目上下文内某一天、同一门店、不同销售和不同收声设备的完整音频分布。

它的核心业务价值是解决相邻收声设备串音问题。

串音问题指：

* 销售 A 的工牌收到了销售 B 正在接待客户的声音；
* 展厅公共麦克风同时收到了多个销售的接待；
* 相邻柜台或试驾车附近的录音设备捕获了同一段对话；
* 一段接待被多个设备重复收录，导致系统误判为多个客户组；
* 串音片段被错误打上销售、客户、事件、标签或单据关联。

核心目标：

* 让用户知道当前片段处在当天接待流程的哪个位置；
* 快速发现同一天、同门店、同时间窗内不同销售和不同设备的重叠录音；
* 判断某段声音是主录音、串音、背景音还是重复收录；
* 快速发现录音空洞、异常高密度、长静音、低置信聚集点；
* 在汽车场景中快速定位试驾、报价、签约、交付等业务事件附近的录音；
* 支持从全局一天缩略图跳转到局部精细调听和标注。

Minimap 展示维度：

* 时间轴：00:00 - 24:00；
* 空间泳道：门店、楼层、柜台、试驾车、交付区、售后区；
* 设备泳道：工牌、展厅麦克风、试驾车录音设备、电话录音；
* 销售泳道：同一门店下的不同销售；
* 人物泳道：销售、客户、未知声纹簇；
* 事件层：接待、试驾、报价、异议、成交、离店、交付、售后；
* 单据层：试驾单、报价单、订单、保险单、交付单、工单；
* 串音层：疑似串音、重复收录、跨设备同声、主录音候选；
* 质量层：低置信、边界冲突、标签冲突、单据不一致、缺失录音。

视觉表达：

* 音频存在：使用连续色块；
* 有效语音密度：使用色块深浅；
* 静音 / 无效录音：使用浅色或空心段；
* 当前播放点：使用垂直播放线；
* 当前精修窗口：使用可拖拽框选区域；
* 异常点：使用小标记点；
* 单据事件：使用单据图标或短标签；
* 同一客户组 / 同一订单链路：使用连线或同色标记；
* 疑似串音：在多个销售/设备泳道之间使用虚线连接；
* 主录音候选：使用更高亮的边框；
* 串音候选：使用半透明或斜纹标记。

交互：

* 点击任意时间点 → 跳转局部波形到该时间；
* 拖拽框选时间段 → 加载该时间段内所有相关音频；
* 横向缩放 → 从一天缩到小时 / 分钟；
* 切换泳道 → 按地点、设备、人员、车辆、单据分组；
* 切换串音视图 → 只显示同门店不同销售/设备的重叠录音；
* 点击事件标记 → 展开相关音频、标签、单据；
* 点击缺口 → 查看是否存在缺失录音或未接入设备；
* 点击低置信聚集点 → 进入低置信优先调听；
* 点击串音标记 → 同步播放多路录音并对齐 ASR、声纹、能量峰；
* 标记主录音 → 指定当前接待应归属的销售、设备和客户组；
* 标记为串音 → 从客户组、标签、单据关联和评测样本中降权或排除；
* 标记为重复收录 → 合并证据链但避免重复计数；
* 点击单据标记 → 打开单据侧栏并定位相关音频；
* 拖动当前精修窗口 → 同步更新下方多轨时间轴；
* 框选后加入上下文篮、评测集或 badcase。

Minimap 不替代下方精细时间轴。Minimap 负责一天级全局定位，下方多轨时间轴负责片段级调听、标注和边界修正。

串音判定参考信号：

* 多设备录音时间高度重叠；
* ASR 文本高度相似；
* 同一声纹在多个设备同时出现；
* 一个设备中目标销售声音较弱，但另一路设备中声音更清晰；
* 两路音频能量峰同步；
* 事件标签和单据实体高度一致；
* 门店空间上设备相邻。

* 专业深色：长时间调听、夜间质检和监控场景；
* 高对比模式：审计、质检和无障碍场景；
* 粒子数据风：洞察、Agent Trace、Minimap、资产血缘和大屏场景。

多语言：

* 首批支持简体中文和英文；
* 文案、错误提示、快捷键说明、Agent 解释、评测报告都必须国际化；
* ASR 文本语言和 UI 语言解耦；
* 标签、事件、单据类型支持项目级翻译。

动效：

* 用于表达状态变化、上下文继承、任务运行、证据链连接和 Agent 推荐；
* 调听、标注、批量确认等高频操作不能被动效阻塞；
* 支持减少动态效果；
* 数据密集页面保持克制，优先保证可读性和操作效率。

粒子风：

* 粒子层必须是数据驱动，不做纯装饰；
* 声音能量可映射为粒子密度；
* 串音可映射为跨销售/设备泳道的粒子连线；
* Agent 推理可映射为证据点向建议点汇聚；
* 资产血缘可映射为上游资产到下游资产的数据流；
* 粒子层必须可关闭，低性能设备自动降级。

智能化交互：

* 根据角色推荐默认首页和视图；
* 根据异常类型推荐数据列表展开路径；
* 自动提示串音排查、低置信优先、单据缺失复核；
* 自动高亮 ASR、标签、单据字段和事件证据；
* 所有智能推荐必须展示原因、证据、置信度和可撤销入口。

25. 当前原型对齐与后续设计基线

当前 React 原型已经从单一调听工作台扩展为完整的 Agentic 音频质检与数据资产平台。后续产品设计以 `当前原型评审与优化计划.md` 作为执行基线，不再把原型理解为单页调听工具。

25.1 当前平台对象边界

当前平台对象应统一为：

* 租户；
* 项目；
* 数据源；
* 数据资产；
* 音频智能服务；
* 任务配置；
* 标签策略资产；
* Prompt 资产；
* 评测运行；
* Human Loop；
* 业务洞察；
* 发布版本；
* 事件关联对象。

其中，业务用户主要操作业务对象；工程、算法和实施角色在高级配置、运行诊断和资产回填中查看底层映射。

25.2 事件关联对象

汽车场景中的报价单、试驾单、订单、合同、金融分期单、保险单、交付单和售后工单，不应作为普通附件处理。它们统一抽象为事件关联对象。

事件关联对象必须能和以下对象建立可解释关系：

* 音频片段；
* ASR 句子；
* VAD / Diar 片段；
* 销售、客户、设备、门店；
* 业务事件；
* 标签；
* 单据字段；
* Agent 建议；
* 数据资产。

因此，设计中所有“单据关联”都应升级为“事件关联”。UI 上必须在 Minimap、证据轨道、ASR 详情、字段差异、数据资产血缘和洞察下钻中保持同一条证据链。

25.3 Audio Intelligence Service

ASR 不再作为单点服务表达，而是统一为 Audio Intelligence Service。

Audio Intelligence Service 内部包含：

* VAD；
* Diar；
* ASR；
* 语言识别；
* 噪音 / 音乐 / 静音检测；
* 串音候选特征；
* 音频质量评分；
* 置信度与错误诊断。

服务层通过 provider 参数切换阿里、火山、自研或开源实现。任务配置只绑定服务版本、provider、参数组和输出契约；服务端点、认证、密钥和裸 URL 在设置模块注册。

25.4 Dagster 暴露原则

底层可以使用 Dagster，但业务页面不应把 Dagster 当成主语言。

业务层使用：

* 任务配置；
* 执行计划；
* 运行记录；
* 输出资产；
* 资产血缘；
* 质量检查；
* 回填任务。

诊断层再披露：

* JobDefinition；
* AssetSelection；
* PartitionsDefinition；
* RunRequest；
* AssetMaterialization；
* AssetCheck；
* IO Manager；
* run tags。

这保证业务人员理解“我在管理证据链和数据资产”，而不是“我在操作工作流引擎”。

25.5 标签优化闭环

标签管理应升级为标签优化闭环，固定主线为：

输入范围 -> Agent 智能抽取/优化 -> 人工修改/确认 -> 效果评价 -> 自动化等级判断 -> 执行/回写 -> 发布/回流

标签体系固定为四层：

* 标签域；
* 标签组；
* 标签；
* 标签值 / 动作。

所有候选标签、Prompt、规则、评测和发布动作都必须保留来源、版本、Trace、人工修改和影响资产。

25.6 原型继续优化原则

后续原型迭代必须先判断问题属于哪一类：

1. 交互语义问题：点击后是聚焦、下钻、生成候选、写回还是发布？
2. 数据模型问题：当前对象是否和租户、项目、任务、资产、版本、Trace 对齐？
3. 智能化问题：Agent 做了什么、人改了什么、效果如何变化？
4. 底层映射问题：是否需要展示执行映射，还是应该隐藏在高级诊断里？
5. 视觉系统问题：是否存在遮挡、串行、低对比、按钮无反馈、大块空白？

只有明确类别后再改 UI，避免继续按截图做孤立修补。

## 26. 基于当前原型的后端开发设计基线

当前 React 原型已经进入后端开发准备阶段。后端设计不再以早期单页调听工具为对象，而是以当前完整中台原型为交互基线，覆盖租户、项目、任务配置、数据管理、知识库、调听证据、标签治理、业务洞察、评测、数据资产和设置。

### 26.1 技术边界

后端基线为：

- FastAPI BFF：承接前端 API、权限、租户项目上下文、UI Projection 和错误格式统一。
- MySQL：主业务库，保存租户、项目、连接器、任务、音频会话、标签、评测、资产、审计和运行状态。
- Redis：缓存、短期锁、幂等 key、异步任务状态和限流。
- MinIO / OBS / S3：保存原始音频、处理后 WAV、ASR JSON、Diar JSON、证据包、报告和导出文件。
- Dagster：底层执行引擎，负责任务版本固化、资产生成、回填、质量检查和运行映射。
- Qdrant：向量检索，负责知识库召回、相似证据片段、标签样本、badcase 和可选声纹 embedding 检索。
- OpenTelemetry：trace_id、run_id、agent_run_id、external_callback_id 的链路追踪。

不使用 ClickHouse 作为默认或推荐组件。洞察和运营大盘第一阶段基于 MySQL 聚合、预计算表、Redis 缓存和 Qdrant 召回解释实现。

### 26.2 业务对象模型

后端第一阶段以当前原型可见对象为准，不再另起一套抽象命名。核心业务对象统一为：

- `Tenant`、`Project`、`User`、`Member`、`Role`、`Permission`：租户、项目、成员和权限隔离。
- `Connector`、`ConnectorRun`、`ExternalCallbackBinding`：数据源接入、同步运行和外部回写。
- `TaskType`、`TaskVersion`、`TaskRun`、`Schedule`、`Experiment`：任务配置、版本、运行、定时和 A/B 实验。
- `DataAsset`、`AssetLineage`、`AssetQualityCheck`、`BackfillRequest`、`ExportJob`：数据资产、血缘、质量、回填和导出。
- `KnowledgeSource`、`KnowledgeChunk`、`KnowledgeIndex`、`KnowledgeQualityGate`、`KnowledgeEffect`：知识源、切片、索引、质量门禁和效果。
- `AudioSession`、`ConversationBoundary`、`EvidenceTrack`、`EvidencePack`、`SpeakerTurn`、`EventLink`：调听证据、边界、轨道、证据包和事件关联。
- `LabelTaxonomy`、`LabelVersion`、`LabelCandidate`、`LabelOptimizationRun`、`ReleaseGate`：标签体系、版本、候选、优化运行和发布门禁。
- `EvalDataset`、`EvalRun`、`MetricResult`、`Badcase`、`FeedbackTask`：评测集、评测运行、指标、badcase 和回流。
- `InsightMetric`、`InsightFact`、`InsightReport`、`EvidenceDrilldown`：洞察指标、事实、报告和证据下钻。
- `HumanReviewTask`、`TraceRef`、`AuditLog`、`OutboxEvent`：人审任务、链路追踪、审计和异步事件。

这些对象的权威状态在 MySQL；向量召回、相似样本和知识检索只在 Qdrant 保存索引和 payload 引用。

### 26.3 MySQL 职责

MySQL 负责所有需要强一致、可审计、可权限控制的业务对象：

- 租户、项目、成员、角色、权限、资源配额和审计日志。
- 连接器配置、授权状态、同步游标、同步运行和错误记录。
- 任务类型、画布版本、任务版本、调度配置、A/B 实验、运行记录和外部回写配置。
- 音频会话、完整对话边界、VAD / Diar / ASR 轨道、事件关联、声纹对象和证据包。
- 标签体系、标签版本、候选标签、冲突、发布门禁、Human Loop 和 ChangeSet。
- 评测集、评测运行、badcase、指标结果、Prompt 版本和回流记录。
- 数据资产目录、资产血缘引用、质量检查、回填、导出和外部回调回执。
- 知识源元数据、切片元数据、索引版本、质量门禁、召回效果和消费路径。

所有核心表必须包含 `tenant_id`、`project_id`、`created_at`、`updated_at`、`created_by`，高风险对象还必须包含 `trace_id`、`version`、`status` 和审计字段。

### 26.4 Qdrant 职责

Qdrant 只负责向量召回，不保存业务权威状态。业务状态仍以 MySQL 为准。

建议 collection：

- `knowledge_chunks`：SOP、FAQ、产品资料、标签样本、证据包切片。
- `evidence_segments`：可回放音频片段、ASR 句子、证据窗口。
- `label_examples`：标签正例、反例、冲突样本、候选样本。
- `badcase_cases`：评测失败样本、人工修正样本、回流样本。
- `voiceprint_embeddings`：可选声纹 embedding，用于候选检索，不作为身份最终判定。

Qdrant payload 必须带 `tenant_id`、`project_id`、`asset_key`、`source_type`、`source_id`、`version`、`trace_id` 和可回跳的业务 ID。前端不直接访问 Qdrant，只通过 BFF 的知识库、标签、洞察或调听 API 获取召回结果。

### 26.5 核心 API 资源

统一使用 `/api/v1/*`、复数资源、kebab-case。读列表必须支持分页、筛选、排序和搜索；写操作必须返回状态、影响范围和 trace。

- `/api/v1/tenants`
- `/api/v1/projects`
- `/api/v1/connectors`
- `/api/v1/task-types`
- `/api/v1/task-versions`
- `/api/v1/task-runs`
- `/api/v1/audio-sessions`
- `/api/v1/conversation-boundaries`
- `/api/v1/evidence-packs`
- `/api/v1/knowledge-sources`
- `/api/v1/knowledge-indexes`
- `/api/v1/labels`
- `/api/v1/label-versions`
- `/api/v1/label-optimization-runs`
- `/api/v1/eval-runs`
- `/api/v1/data-assets`
- `/api/v1/insights`

### 26.6 异步运行与状态

后端必须统一异步状态模型：

- `pending`：已创建，等待执行。
- `running`：执行中。
- `success`：完成并写入结果。
- `failed`：失败，可重试或查看错误。
- `blocked`：被权限、门禁、依赖或审批阻断。
- `cancelled`：用户或系统取消。

任务运行、Agent 运行、评测运行、知识索引构建、导出、回填、外部回写都使用同一状态语义，前端才能稳定映射 pending、success、failed、retry、blocked。

### 26.7 模块到后端的最小闭环

- 任务配置：TaskType、TaskVersion、TaskRun、Schedule、Experiment、OutputBinding、CallbackBinding。
- 数据管理：AudioSession、PersonVoiceprint、EventLink、BusinessDocument、AggregationView。
- 知识库：KnowledgeSource、KnowledgeChunk、KnowledgeIndex、KnowledgeQualityGate、KnowledgeEffect。
- 调听：ConversationBoundary、EvidenceTrack、LabelSpan、SpeakerTurn、AgentSuggestion、ReviewDecision。
- 标签：LabelTaxonomy、LabelVersion、LabelCandidate、LabelOptimizationRun、ReleaseGate、HumanReviewTask。
- 评测：EvalDataset、EvalRun、MetricResult、Badcase、FeedbackTask。
- 洞察：InsightMetric、InsightFact、InsightReport、EvidenceDrilldown。
- 数据资产：DataAsset、AssetLineage、AssetQualityCheck、BackfillRequest、ExportJob。
- 设置：ModelProvider、AudioIntelligenceService、ToolRegistry、PolicyGuard、SecretRef、AuditLog。

### 26.8 执行引擎暴露原则

底层可以使用 Dagster，但业务 API 不以 Dagster 为主语言。业务接口返回任务配置、执行计划、运行记录、资产生成、质量检查和回填任务；只有在执行映射、运行诊断、资产血缘和工程视图中返回 Job、AssetSelection、Partition、RunRequest、AssetCheck、IO Manager 等字段。

后端第一阶段优先支撑当前原型可见主流程，不一次性实现全部高级诊断能力。
